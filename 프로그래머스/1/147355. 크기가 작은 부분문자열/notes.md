# 크기가 작은 부분문자열 (147355)

## 상태
- 제출 완료 (`long.Parse` + `Substring(i, p.Length)`, `i < t.Length - p.Length + 1`)
- 공식 폴더: `프로그래머스/1/147355. 크기가 작은 부분문자열/`
- 1.27 ms, 49 MB

## 내가 한 질문
- 잘라 배열 만들고 순회하면 2N? 시간이랑 횟수로 나누던 성능 평가가 뭐였지?
- 위치로 자르는 string 메서드. `int.Parse`로 매번 바꿔 비교? `p`는 먼저 변환? 총 크기는 `t길이 - p길이 - 1`?
- 자리 수에 따른 정수 자료형 정리.
- 자료형 안 바꾸고 비교하는 특수 경우? 같은 자리 수만? 자리 수가 바뀌면?
- `"000"` 같은 조각도 있지 않나. 이번엔 문자열만 비교해도 되나?
- 자리 수가 커지면 문자열이 더 빠르지 않나?
- 인덱스 비교가 뭐지? 예시에서 `i`가 뭐지? 코드가 빠진 것 같다.
- 자리 수를 맞춘 뒤 숫자 비교하는 시스템도 있나?
- 제출 화면의 ms와 MB는?

## 막혔던 지점
- 겹치지 않게 쪼개는 게 아님. 한 칸씩 미는 창. 개수는 `t길이 - p길이 + 1`. `- 1`이면 마지막 창이 빠짐.
- `O(2N)`은 `O(N)`. 계수는 떼고, 횟수가 N에 따라 늘는지가 시간 복잡도. 배열을 얼마나 쓰는지가 공간 복잡도.
- `Substring(시작, 길이)`. 끝 인덱스가 아님. 접두사 확인·동영상 재생기와 같음.
- `p` 길이 최대 18 → `int`(약 10자리) 오버플로. 제출은 `long.Parse`.
- `"02"`는 숫자 2. `long.Parse("02") == 2`.

## 문제 한 줄
`t`에서 `p`와 같은 길이 부분문자열 중, 값이 `p` 이하인 개수. `"02"`는 2로 본다.

## 핵심 패턴 (제출)
```text
pNum = long.Parse(p)
i = 0 .. t.Length - p.Length   (개수 = 길이차 + 1)
  partNum = long.Parse(t.Substring(i, p.Length))
  partNum <= pNum 이면 answer++
```

## 같은 자리 문자열 비교 (확장)
길이가 같으면 `"141" vs "271"`은 앞글자부터 비교해도 숫자 순서와 같음. `'0'`~`'9'`가 크기 순.
자리 수가 다르면 `"9" > "10"`처럼 깨짐. 짧은 쪽 앞에 0을 채우거나, 앞 0을 빼고 길이를 먼저 비교.
이번 문제는 창 길이가 `p`와 같아서 패딩이 필요 없음. `"000"`도 `'0'`이 작아서 숫자 0과 맞음.

인덱스 비교: `Substring` 없이 `t[i+k]`와 `p[k]`. `i`는 창 시작, `k`는 창 안 위치. 할당이 없음.
`Parse`는 글자를 끝까지 읽고, 문자열/인덱스 비교는 다른 자리에서 끝낼 수 있음. 이 제한(1만×18)에선 체감 차이 없음.

## 제출 화면
- `ms`: 실행 시간
- `MB`: 그 테스트가 쓴 메모리. 기본 런타임만으로도 수십 MB. 제한 초과만 실패.

## 다음에 볼 것

- 자리 수 10 넘으면 `int` 대신 `long`. 19자리 이상이면 문자열 비교 또는 큰 수.
- 길이가 다른 숫자 문자열: 패딩 / 길이 먼저.
