## 내가 한 질문
- 성능이 문제. 자료구조로 배열 교환이 관건. calling 한 번에 끝내고 싶다(최대 100만). Dictionary는 굳이? 호출 카운트 +/− 후 마지막에 2n으로?
- 코드로 보여 줘
- 배열도 바꾸고 Dictionary 값도 바꾸나?
- Dictionary는 자주 업데이트되는 곳에 쓰지 말라던데, 그 정도가 어느 정도?
- 키 총수가 고정이면 잦은 수정도 그나마 괜찮은가?

## 문제 한 줄
`callings`에 이름이 불릴 때마다 그 선수가 **바로 앞**과 자리를 바꾼다. 최종 1등→꼴등 이름 배열 반환.

## 성능
- players ≤ 50,000, callings ≤ 1,000,000
- calling마다 배열 선형 탐색 → O(P·C) → **TLE**
- Dictionary로 등수 O(1) + 인접 교환 → **O(C)** 정석

## 왜 “카운트 후처리”는 안 되나
추월은 **그 순간의 앞사람**과 바꿈. 순서가 바뀌므로  
“불린 횟수 +/−를 모아 마지막에 반영”하면 앞사람이 谁인지 사라져 **오답**.

## 자료구조 (둘 다 갱신)
| 구조 | 의미 | calling 시 |
|------|------|------------|
| `players[등수]` | 등수 → 이름 (답) | 앞과 교환 |
| `indexByName[이름]` | 이름 → 등수 | 두 선수 등수 갱신 |

배열만 / Dictionary만 바꾸면 다음 조회나 최종 답이 깨짐.

```text
idx ← indexByName[name]
front ← idx - 1
players 교환
indexByName[name] = front
indexByName[frontName] = idx
```

## Dictionary “자주 업데이트” 조언 정리
- **금지 뜻이 아님**. 값만 자주 덮어쓰는 건 코테에서 흔하고 OK
- 키가 **고정**(이번: 선수 n명) + 값만 수정 → 100만 번도 괜찮음
- 부담되는 쪽: 키를 자주 추가·삭제 / Dictionary를 매번 재생성 / 키가 0..n-1이면 배열이 더 나음
